# Architecture Decision Sheet
*Phase 1 deliverable — answers to Part 0.35 of the architecture guide, scoped for this as a portfolio/demo build. Real numbers are marked [ASSUMED] where a production deployment would need actual business input instead.*

## Business & Scope
1. **Business outcome:** Demonstrate an enterprise-grade agentic system that resolves order exceptions (payment/inventory/carrier/return/fraud) faster and more consistently than manual CS triage, with full auditability. Success = golden-eval-set pass rate, correct temporal policy resolution, zero duplicate-action incidents under chaos testing.
2. **End user:** CS Ops team (case queue/escalation UI) + customers (indirect, via faster resolution + comms). No real users yet — this is a portfolio build; UI is built to spec regardless.
3. **Out of scope (v1):** legal/chargeback disputes above $[ASSUMED: 500], autonomous fraud account bans (recommend-only), cross-border customs/duty exceptions.
4. **Ownership:** Engineering + business owner are the same person (portfolio project) — in a real deployment these would be split per the architecture doc's explicit recommendation.

## Risk & Autonomy
5. **Blast radius:** Medium — synthetic data only, no real payments/customers in this build, so blast radius in *this* environment is zero; the architecture is designed as if it were real (Stripe/carrier **test mode** throughout).
6. **Always-human actions:** fraud-flag account actions, anything above the $ ceiling, anything below confidence threshold τ. **Auto-safe:** carrier label generation, low-value refunds within policy.
7. **Regulated:** PCI-DSS-adjacent (payment metadata path, no raw card data), consumer-protection return-rights law. Simulated via Stripe/carrier test-mode APIs, no real compliance exposure in this build.
8. **Worst headline:** "AI agent denies a valid return because it read the wrong policy version" — this is exactly the edge case the temporal-versioning design (RAG 8.2.3) exists to prevent, and is the primary acceptance test for Phase 3.

## Data & Knowledge
9. **Data access:** Synthetic orders/customers generated by this build; service-account-scoped MCP tools, least-privilege by design even though the backing systems are mocks.
10. **Knowledge freshness:** Policy docs change infrequently (weeks); inventory/carrier/payment status is real-time (webhook-driven).
11. **PII/PHI:** Synthetic PII only in this build; architecture treats it as real (redaction before logging, per 8.8) so the pattern transfers directly to production data.

## Architecture & Constraints
12. **Latency budget:** Diagnosis+decision <60s [ASSUMED, generous — not customer-facing real-time chat]; execution confirmation within external API SLA.
13. **Cost ceiling:** $0/month target — entire stack built on free tiers + self-hosted components (architecture doc 8.10). Cost canvas below.
14. **Simplest architecture:** Mixed — workflow for execution, agent loop for diagnosis only (Part 1's per-sub-workflow calibration). Named reason: diagnosis genuinely can't be flowcharted in advance (next check depends on last result); execution can and must be deterministic (financial write risk).
15. **≥3 failure modes:** duplicate refund on retry (→ idempotency keys, Phase 8), stale policy retrieved (→ temporal metadata filtering, Phase 3), runaway diagnosis loop (→ hard step ceiling, Phase 6).

## Operations & Lifecycle
16. **Pre-launch eval:** Golden set from the edge-case inventory (Phase 15), minimum bar = 100% pass on the 3 highest-signal scenarios (temporal policy, idempotent refund, fraud-vs-LTV).
17. **Post-launch monitoring:** N/A for portfolio build — documented as a runbook (Phase 17) rather than operated live.
18. **Rollback:** Feature-flag disable of auto-execution, target <5 min — tested in Phase 16.
19. **Dependency deprecation plan:** Free-tier model/rate-limit changes are the primary risk (noted throughout 8.10) — pluggable LLM client interface (Phase 6) means swapping providers is a config change, not a rewrite.

## Cost Canvas (Layer 14) — Portfolio-Scale Estimate

`Monthly Cost ≈ W × A × U + P + F`

| Variable | Portfolio-scale assumption |
|---|---|
| **W** (Workload) | ~50 synthetic exceptions/day [ASSUMED demo volume] |
| **A** (Amplification) | ~6 tool calls/case (parallel diagnosis fan-out) + 1 resolution reasoning call + 1 comms call ≈ 8 model-touching steps/case |
| **U** (Unit economics) | Free-tier models throughout (Groq router, Mistral Large reasoning, Gemini Flash generation) — $0 direct cost within free-tier limits |
| **P** (Platform floor) | $0 — self-hosted SQLite/Qdrant-local/BGE-M3 in this sandbox; Postgres/Redis/Qdrant via free-tier or local Docker in a real deployment |
| **F** (Failure tax) | Budgeted qualitatively: retry rate tracked from Phase 8's chaos tests, human-escalation "cost" simulated as a manual review step in Phase 13's UI walkthrough |

**Target: $0/month at portfolio-demo volume** (~1,500 exceptions/month), with the free-tier rate-limit ceilings (8.10) as the actual binding constraint rather than dollar cost — e.g., Groq's ~1K RPD and Mistral's 1 req/sec are the real capacity limits to watch, not billing.

## Auto-Execute Threshold Starting Values (informs Phase 7/9)

| Setting | Starting value | Rationale |
|---|---|---|
| Confidence threshold τ | **0.90** | Conservative default — widen only after the learning loop (Phase 9) proposes and a human accepts an increase for a specific case cluster |
| Auto-execute $ ceiling | **$50.00** | Conservative default for a demo; a real deployment would set this from actual average-order-value and refund-fraud-loss data |

*(Both values are already wired as defaults in `app/core/config.py` — this document is the paper trail for why those specific numbers were chosen, not just where they live in code.)*
